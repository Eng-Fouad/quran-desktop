# Source data for `core.db`

`core.db` (the bundled Quran text, layouts, glyph codes and divisions; docs/ARCHITECTURE.md §3.1) is generated by
`cargo xtask build-core` and never committed (BRIEF §4). Two source adapters fill the same schema and run the same
`verify-core` gates G1–G16:

| Source | Command | Inputs | Use |
|---|---|---|---|
| `qdc` | `pnpm core:qdc` | QDC API responses, cached in `data/cache/` (refetched after 7 days) | local development only |
| `qul` | `pnpm core:qul` | QUL exports placed by a person in `data/sources/qul/` | release builds |

**`qdc` builds are for your machine only.** The Quran Foundation Developer Terms forbid distributing their content or
anything built from it. Never commit, upload, attach or share a qdc `core.db`, `data/cache/` or the fixtures made from
them.

## Release inputs: `data/sources/qul/`

[`qul/manifest.toml`](qul/manifest.toml) lists every input with its QUL resource id and SHA-256. The data files are
gitignored (everything in `qul/` except `manifest.toml` and `.gitkeep`). Every QUL download needs a free account, so a
person has to fetch them. Automated agents must not create the account or sign in.

| Manifest key | File | Download | Format | Used for |
|---|---|---|---|---|

| `layout.v1` | `layout-15.sqlite` | [mushaf-layout 15](https://qul.tarteel.ai/resources/mushaf-layout/15): KFGQPC V1 layout (1405H print) | SQLite | V1 pages and lines |
| `layout.v4` | `layout-19.sqlite` | [mushaf-layout 19](https://qul.tarteel.ai/resources/mushaf-layout/19): KFGQPC V4 layout (1441H print) | SQLite | V4 (tajweed) pages and lines |
| `script.code_v2` | `script-61.sqlite` | [quran-script 61](https://qul.tarteel.ai/resources/quran-script/61): QPC V2 Glyph - Word by Word | SQLite | `word.code_v2`; maps the layouts' word ids |

Take care with two resources:

- **Imla'i: use 54, not 60.** "Imlaei simple" (60) writes the dagger alef as a full alef and pre-folds hamza seats
  (`الرحمان`, `ذالك`, `يومنون`). With it, searching for `الرحمن` finds nothing (docs/deviations/WP3a.md §1).
- **Rub: use 63, not 67.** Metadata 67 is QUL's *Hizb* file (60 hizbs). The 240 rub el hizb quarters are 63.

The build rejects the wrong id in the manifest and names the right one. If you download a file of the wrong kind, its
contents are rejected too: a hizb file in the rub slot has 60 records with `hizb_number`, not 240 with `rub_number`.

The file names are suggestions; the manifest maps each key to a name. Layouts must be SQLite. Scripts should be SQLite;
QUL's JSON exports are accepted, but a JSON layout export is a folder of pages and is not. Metadata may be JSON or
SQLite.

### Steps

1. **Account.** A person signs in at <https://qul.tarteel.ai> with a free account.
2. **Download** each QUL resource in the table from its page, in the format shown. Rename it to the manifest's file
   name and put it in `data/sources/qul/`. You may leave out the three optional files (`juz`, `hizb`, `manzil`); then
   delete their lines from the manifest, and the build reports that juz, hizb and manzil were not cross-checked.
3. **Tanzil.** Put [`quran-data.xml`](https://tanzil.net/res/text/metadata/quran-data.xml) (77,234 bytes) into
   `data/sources/qul/`. A qdc build has already cached the same file at `data/cache/tanzil/quran-data.xml`, so you can
   copy it from there. Its SHA-256 is already in the manifest.
4. **Record the hashes.** Run `pnpm core:qul` once. It stops before reading anything and prints the actual SHA-256 of
   every file whose hash isn't recorded yet. Check that each file is the resource named in its line, then paste each
   hash into its `sha256 = ""`. You can also compute the hashes yourself:
   - PowerShell: `Get-FileHash -Algorithm SHA256 data/sources/qul/* | Format-List Hash, Path`. Upper-case hex is fine.
   - Git Bash, macOS or Linux: `sha256sum data/sources/qul/*` (macOS: `shasum -a 256 data/sources/qul/*`).
5. **Build.** Run `pnpm core:qul`, which is `cargo xtask build-core --source qul`. It writes
   `src-tauri/resources/core.db` and runs every `verify-core` gate.

When QUL publishes a new export, replace the file and record its new hash. The build refuses a file whose hash differs
from the manifest, so the inputs of a release `core.db` are always the files that were checked. Their combined hash is
stored as `meta.source_manifest_sha256`.

### What the build checks

Before any `verify-core` gate runs, the qul adapter (`xtask/src/build/qul.rs`) requires all of the following:

- **Manifest.** Every file exists and matches its recorded SHA-256, and every `resource` is the expected QUL id. All
  problems are listed in one run.
- **Word scripts.** The four scripts list the same word locations (`surah:ayah:word`). Words are joined by location,
  never by QUL's numeric ids. There must be exactly 83,665 locations (77,429 words and 6,236 end markers). The last
  word of every ayah is its end marker.
- **Word ids.** The layouts give each line's words as a range of QUL `word_index` values. Those are mapped through
  script 61 (or through the layout's own `words` table, if it has one), and `word_index` order must equal reading
  order.
- **Layouts.** Each layout has 604 pages. Every page has exactly 15 lines, except pages 1 and 2, which have 8.
  `line_type` must be `ayah`, `surah_name` or `basmallah`. QUL's `''` placeholders count as empty. Then the shared
  derivation (`derive.rs`) checks the line kinds against the surah-header rule (C15) and checks the centring.
- **Divisions.** The rub, juz, hizb and manzil records cover every ayah exactly once, in order. Their `verses_count`
  and `verse_mapping` must agree with the ranges. The rub comes from QUL. Juz, hizb and manzil come from Tanzil and
  are cross-checked against QUL's files, with zero differences allowed. The one known rub difference from Tanzil
  (rub 106: 15:49 vs 15:50) is allowlisted in `xtask/data/division_exceptions.toml`.

### When the build stops

| Message | What to do |
|---|---|
| `sha256 not recorded yet` / `but the manifest records …` | Check the file, then record its hash (step 4). |
| `resource 60, expected 54` / `resource 67, expected 63` | Download the right resource (see above). |
| `the word scripts must have identical location sets` | One script is from another export or format. If only end markers are missing, use the SQLite download. |
| `the word scripts have 83668 word locations, expected exactly 83665` | QUL numbers 3 more word slots than there are words (FACT C7: near 3:1:1, 8:7:1 and 14:1:1). The message lists the locations that look extra. Don't edit the files by hand. Take the list to the project lead, who decides how to map them and records the decision in `docs/deviations/`. |
| `word_index order and location order disagree` | Script 61 and the layouts come from different exports. Download them again together. |
| `page N has no line(s) …`, `line_type …` | The layout export is incomplete or in an unexpected shape. Download it again in SQLite format. |

## Licensing and permission

**Status: permission not obtained yet. Do not distribute a `core.db` built with `--source qul`.**

- The QUL code is MIT-licensed. QUL publishes no licence for the data resources listed above. Their copyright pages
  say QUL has no copyright information for them, and the FAQ asks users to check each resource. The Mushaf data
  originates from the King Fahd Glorious Qur'an Printing Complex (KFGQPC).
- Before a release ships a `core.db` built from these files, get written permission from Tarteel/QUL, and ideally from
  the Quran Foundation (FACT_SHEET open question 1). Record it here: who granted it, the date, what it covers, and
  where the correspondence is kept.
- Until then the files stay out of git (`.gitignore`: `data/sources/qul/*`). Remove that rule only if the permission
  allows the files to be committed.
- Tanzil `quran-data.xml` is licensed CC BY 3.0, and its attribution goes into `meta.licence_note`, which the build
  writes. Its download needs no login, and the licence allows verbatim copies.

## Other folders

`data/sources/tanzil/` comes from the project scaffold. `build-core` does not read it. The qul build reads Tanzil from
`qul/quran-data.xml`, and the qdc build reads it from `data/cache/tanzil/`.
