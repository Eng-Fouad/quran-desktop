# Critic

## Contradictions resolved
- V1 vs V2 page/line layout: mushaf-text-layout said v1_page==v2_page on all sampled pages, and mushaf-fonts said mushaf=1 and mushaf=2 have identical word-to-line mapping on 16 pages. Both are wrong. A full-Quran scan of api.quran.com/api/v4/verses/by_chapter/{1..114} (word_fields v1_page,v2_page,line_v1,line_v2) shows V1 (1405H) and V2 (1421H) page starts differ on 25 pages (121,122,123,145,532,533,534,565,568,570,576,584,586,588,589,590,592-600), covering 56 ayahs / 361 words. Line breaks also differ, e.g. 76/94 words on p600. Evidence: critic/v1v2_summary.json, v1v2_page_starts.json.
- Tanzil page starts: proposed as the CI cross-check for the V2 layout. Tanzil quran-data.xml matches V1 page starts 604/604 and V2 only 579/604, so the gate must compare QUL layout 15 (V1) to Tanzil, and V2/V4 to their own tables. Evidence: critic/tanzil_vs_v1_v2_page_starts.txt.
- Legacy api.quran.com by_page vs QDC by_page: the legacy /api/v4/verses/by_page/{p} picks verses by V1 page but returns V2 line numbers. On p600 it drops 100:6-9, leaving lines 1-2 empty. https://api.qurancdn.com/api/qdc/verses/by_page/{p}?mushaf={1|2|19}&per_page=all paginates correctly for each mushaf. Evidence: critic/p600_default.json, qdc_p600_m1.json, qdc_p600_m2.json, pg599.json.
- V4 tajweed layout: mushaf-text-layout implied V4 could reuse V2 lines. QDC mushaf=19 vs mushaf=1 share page starts but 0-6 words per page sit on different lines (p528: 6, p586: 5, p600: 3), so V4 needs its own layout (QUL layout 19).
- Word glyph codes: mushaf-fonts said each word span holds exactly one glyph character. In fact 4,517 V2 words and 4,580 V1 words have 2-4 PUA chars (waqf/sajda marks are separate glyphs, e.g. 38:24:32 V2 = U+FCBA U+FCBB). Codes must be stored as TEXT and rendered whole.
- No-login fallback: mushaf-text-layout recommended stream-parsing QUL mini_quran_dev.sql.zip. I streamed the full 201,979,245 B dump. It is a sparse dev subset: verses 1,923 rows (1:1-12:20), words 22,221, mushaf_words 572 rows (mushafs 2 and 6 only). The fallback is not viable.
- QUL word count: estimated at ~83,664-83,668. Verified: the API has 83,665 word rows (77,429 word + 6,236 end), while QUL word_index runs 1..83,668 (114:6:4=83668). There are 3 extra slots relative to API order (offset +1 by 3:1:1, +2 by 8:7:1, +3 by 14:1:1), so joins must use location s:a:w.
- Basmala in QDC chapter files: audio-sources marked this [?] (inferred). Now verified by byte-duration arithmetic: qdc Afasy 112.mp3 = 214,038 B at MPEG1-L3 128k = 13.38 s, EveryAyah 112001-112004 sum = 13.48 s, basmala 001001 = 9.18 s. No basmala. For all 12 QDC reciters checked, 112:1 word 1 starts at 0-40 ms.
- Cargo availability: rust-data-search said cargo is not installed, while tauri-platform and rust-audio-media compiled with it. cargo/rustc 1.99.0 exist in %USERPROFILE%\.cargo\bin, which is just not on the Git-Bash PATH. A rusqlite 0.40.2 bundled probe compiled and ran.
- AppImage size: tauri-platform said it grows past 70 MB with bundleMediaFramework; rust-audio-media said +15-35 MB. The Tauri docs say AppImage itself grows to 70+ MB, and schema 2.12.2 says bundleMediaFramework adds ~15-35 MB. With native Rust audio it isn't needed.
- Vite build.target: tauri-platform copied the Tauri guide's chrome105/safari13; frontend-ux said keep the Vite 8 default. Keep Vite 8's 'baseline-widely-available' (chrome111/safari16.4) and raise macOS minimumSystemVersion to 13.3.
- Core DB packaging: mushaf-text-layout and tauri-platform proposed .zst plus first-run decompression; rust-data-search proposed uncompressed. Tauri schema 2.12.2 confirms the NSIS compression default is 'lzma'. Ship uncompressed and open in place with ?mode=ro&immutable=1.
- Search seed text: QUL 53 (Uthmani simple) vs Imla'i. text_uthmani_simple 1:2 ends 'العلمين' while text_imlaei_simple ends 'العالمين', so use QUL 60/54 (Imla'i).
- MSRV: 1.90 (tauri) vs 1.91 (stream-download) vs 1.95 (rusqlite_migration). crates.io shows rusqlite_migration 2.6.0 rust_version 1.95, so set workspace rust-version 1.95 and pin the toolchain to 1.99.0.
- Font host: verses.quran.foundation vs quran.com/fonts. Both serve identical bytes, but only verses.quran.foundation sends ACAO *. static.qurancdn.com 404s for v4/colrv1. Primary is verses.quran.foundation, downloaded from Rust.
- Surah header/basmala line source: assumed to need QUL mushaf_line_alignments. Deriving line types from empty lines before each surah's first ayah line holds for all 114 surahs in V1 and V2. The gap is 2 lines (1 for surahs 1 and 9), always on the same page, and there are no other empty lines (224 total).
- Dev server port 1420 vs 5173: use 1420 with strictPort, consistent with the tauri init -P flag.
- Core schema: the proposals put page/line on word or ayah. Because of the V1/V2/V4 differences, page and line must live in per-mushaf tables (page, line keyed by mushaf_id). A unified schema is in FACT_SHEET.md section 2.4.

## Gaps
- Licensing permission for QUL layout and glyph-code data (layouts 10/15/19, scripts 61/57/312/60, metadata 63-70): QUL publishes no licence and the data originates from QF/KFGQPC. Written confirmation from Tarteel/QUL (and ideally QF) is needed before shipping core.db.
- QUL downloads require a human login. There is no complete no-login source for the full V2/V4 layout and glyph codes: the public mini dump is a sparse subset, and QF API responses cannot legally be bundled. The ISC npm package quran-madina-html@1.0.1 has only a V1 (1405H) line layout with Tanzil text and unclear provenance, so it is usable only as a cross-check.
- is_centered flags for V1 and V4 come only from QUL layouts 15/19. For V2, the quran.com constant list plus pages 1-2 is the only verified source.
- Decorative fonts (QCF_SurahHeader ©KFGQPC, QUL quran-common with no licence string, quran.com sura_names with no licence) have no clear redistribution licence. Download them on demand with the QCF pack, with our own SVG cartouche plus Unicode basmala/surah-name fallbacks in the installer.
- WebKitGTK (Linux) support for COLRv0 and font-palette is untested. A runtime canvas probe with V2 fallback is required.
- Identity of the 3 extra QUL word_index slots (around end of S2/3:1, before 8:7, before 14:1) is unknown, because the full QUL words file needs login.
- QF Content Sync needs a QF Developer Console account, production approval and a backend proxy holding the client secret (Cloudflare Worker) before QF-only tafsir/WBW can be offered offline.
- No recitation source grants redistribution rights (QuranicAudio says personal use; QF forbids redistribution). Audio must be streamed and cached per user only.
- The Tanzil Quran text download requires accepting Tanzil's terms (agree=true). The user must perform this, not an agent.
- Not researched: Windows Authenticode signing, Apple notarization and entitlements, updater signing keys, Linux CI images (Ubuntu 22.04) and packaging tests.
- macOS/Linux runtime behaviour (custom protocol, audio engine, media controls) and the signalsmith-stretch libclang build are untested; all probes ran on Windows 11.

## Open risks
- Legal: core.db built from QUL data that has no published licence and originates from QF/KFGQPC. QF terms (updated 2026-10-04, can change again) forbid bundling QF Content and treat indexes as Derived Materials. Ship only after written permission and with attribution to QUL, QF, KFGQPC and Tanzil.
- Legacy api.quran.com / api.qurancdn.com are QF-operated (x-qf-origin header), unauthenticated today, and may be deprecated with short notice. Use them only for dev, verification or emergency fallback.
- Layout mixing: V1/V2/V4 differ in page starts (25 pages, V1 vs V2) and line breaks (V4 vs V2). Any table not keyed by mushaf_id, or any use of legacy by_page, will render broken pages.
- Multi-glyph word codes (up to 4 PUA chars) break renderers or highlighters that assume one char per word.
- The 3 unexplained extra QUL word_index slots mean word ids from the API and QUL are not interchangeable. Join on location only.
- Decorative and page fonts are ©KFGQPC. QF allows bundling or caching only with an active Developer Console account plus credit, and never via our own asset package or download server. quran-common and sura_names carry no licence text.
- WebKitGTK COLRv0/font-palette support is unverified. Safari 17.0-17.1 has a COLRv0 regression, and WKWebView has no COLRv1: if upstream swaps v4/colrv1 to true COLRv1, macOS tajweed breaks. Record the COLR version per downloaded file.
- Audio rights: QuranicAudio says personal use only, and QF forbids redistribution. Upstream files get replaced (quran_android audio_updates manifest), which silently invalidates paired timings. Re-check Content-Length/ETag.
- tauri-specta/specta are RC (rc.25) and Tauri 3.0 alpha exists. TypeScript 7 is npm latest but incompatible with svelte-check and typescript-eslint. Pin everything exactly.
- The native audio engine (cpal/symphonia/signalsmith-stretch) has only been cargo-checked on Windows. signalsmith-stretch needs libclang and was not built. macOS/Linux untested; keep the WSOLA fallback.
- panic='abort' in release turns any unwrap in a command or protocol handler into an app crash.
- Windows MAX_PATH (260): SQLite's Windows VFS and native tools fail on long paths. Keep the project and data paths short.
- Temp working files from this critic pass remain in C:\qdc (~250 MB, including the QUL dump zip, a chapter cache and the ftsprobe build). Removal was blocked as a protected path; the user can delete C:\qdc manually.
