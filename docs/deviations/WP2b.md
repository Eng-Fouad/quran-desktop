# WP2b deviations (UserDb core, study data and settings)

## Deviations from ARCHITECTURE.md

1. **Acceptance command syntax (§14.3).** `cargo test -p quran-core --lib user_db::migrations user_db::positions …` and
   `cargo test -p quran-desktop --lib commands::settings commands::user_study` are rejected by cargo 1.99 ("unexpected
   argument": cargo takes one `TESTNAME`). They were run as `cargo test -p quran-core --lib -- <filters…>` and
   `cargo test -p quran-desktop --lib -- commands::settings commands::user_study` (libtest takes several filters), as
   WP1a/WP1c also report.
2. **`UserDb` internals (additive).** The handle also holds a shared clock: `UserDb::now_ms()` (public; every `user_db`
   file uses it) and `#[doc(hidden)] UserDb::set_test_clock(Option<i64>)` (tests pin time, shared by clones; production
   never calls it). `impl Debug for UserDb`.
3. **Additive `quran_core::user_db` API** (lib.rs unchanged; reachable through the public `user_db` module):
   - `settings_replace(&Settings) -> (previous, stored)`: read + validated write in **one transaction**, so
     `settings_set` hands its hooks a consistent pair; `settings_save` is `settings_replace(..).1`.
   - `settings_reset() -> (previous, current)` (see 5), `RESET_PRESERVED_KEYS`, `SETTING_FIELDS`, `SettingField`.
   - `SettingField { key, get: fn(&Settings) -> serde_json::Result<Value>, set: fn(&mut Settings, Value) ->
     serde_json::Result<()> }`: `get` returns a `Result` instead of the spec's bare `Value` (no unwrap on serialisation).
     The table is generated by a macro that also destructures `Settings` exhaustively in a test, so a new field without
     a row fails to compile; unit tests also check it against the IPC JSON keys.
   - Pack registry: `pack_installed(id)`, `pack_item(pack, item)` (single-row reads) and `pack_items_clear(pack) -> u32`
     (one statement instead of N deletes when a pack is removed).
   - Memorisation: `MemoSchedule`, `schedule_review(prev, rating, now_ms)` (the pure §5.10 table), `MAX_STRENGTH`,
     `MEMORIZED_STRENGTH`.
   - `restore_from(src)` (see Requests: no command exists for it yet), `TOMBSTONE_RETENTION_DAYS`.
4. **Settings storage is sparse.** No row = the default. A save writes a key only when its JSON differs from the effective
   stored value (the row, or the default when there is none): saving the defaults on a fresh DB writes nothing, fields the
   user never touched follow future default changes, and an unparsable row is rewritten (self-healing). Missing keys are
   normal and not logged at warn (a fresh install would otherwise warn ~50 times per load); invalid rows are. Loaded
   settings are `validated()`, so values stored under older limits are clamped on the way in.
5. **`settings_reset` keeps `ui_language`, `onboarding_done`, `hints_seen`, `close_to_tray_asked`** (it deletes every other
   row). They record the user's language and what the app has already shown or asked; resetting them would re-run
   onboarding, replay every hint and switch the UI language under the user (§5.13 does not define reset; this is the
   chosen semantics).
6. **`settings_set`/`settings_reset` are serialised** by one async gate held across write → hooks → event, so overlapping
   calls apply their hooks as one chain (`prev₂ == next₁`). A failed write applies no hook and emits nothing.
   `SettingsChanged(next)` is emitted after every successful write (also when nothing changed), as §5.13 says.
7. **Events.** Events are emitted with `tauri::Emitter::emit(E::NAME, ..)` (same name and payload as tauri-specta's
   `Event::emit`, which `expect`s its registry), after the write committed. `UserDataChanged` kinds: history **and
   search history** → `history` (the frozen `UserDataKind` has no search-history kind), memorisation and self-tests →
   `memo`, presets → `presets`. `user_backup_create` changes no user data and emits nothing.
8. **Positions.** `position_set` validates ayah 1..=6236 and page 1..=604; `updated_at` is stamped (input ignored).
   `positions()` is in context order (mushaf, translation, audio); an unknown stored `mushaf_id` reads as no layout.
9. **History.** "Same page within 10 min" is: same mode and same layout + page (the same ayah when there is no page) as
   an entry from the last 10 minutes. The merged entry moves to the top (newest id) with the summed dwell and the latest
   ayah, so paging back and forth never duplicates pages. At most 10,000 entries are kept (oldest dropped).
   `history_list`: newest first by id, `limit` capped at 1,000 (0 → none), `before_id` pages backwards.
10. **Search history.** The query is trimmed with whitespace runs collapsed (case and diacritics kept). Blank queries,
    queries over 500 characters and a translation scope with a blank pack id are `InvalidArgument`. At most 200 entries
    (least recently used dropped); `limit` capped at 200. Rows whose scope kind this build does not know are filtered in
    SQL (so `limit` still counts usable rows).
11. **Memorisation.** `memo_progress` returns stored rows only (sparse; no row = `new`, strength 0), while
    `memo_set_status`/`memo_review` return one entry per ayah of their range. `memo_set_status`: `new` deletes the rows
    (full reset); `learning` caps strength at 3 and makes the ayahs due now; `memorized` raises strength to ≥ 4 and
    schedules like a "good" review (`now + 2^s` days); `review` makes them due now (stored status `review`). Review counts
    and lapses are kept. `mistakes` in `MemoReviewInput` is informational (the table uses the rating only).
    `memo_test_finish` does not touch the schedule (the UI rates the range with `memo_review`); finishing a finished test
    is `InvalidArgument`, an unknown id `NotFound`. `memo_test_start` validates the range before `fastrand` (which panics
    on an empty range).
12. **Loop presets.** Name trimmed, 1..=100 characters, and a valid ayah range, else `InvalidArgument`. Repeats, speed and
    gap are **normalised like the settings** (clamped/rounded with `quran_types::limits`) rather than rejected. Unknown
    ids on update/delete are `NotFound`. Ordered by name (case-insensitive), then id. Hard delete (no tombstone column).
13. **Pack registry semantics.** `pack_delete` removes only the `installed_pack` row: `pack_item` rows are independent
    (stream-cached audio items exist for packs that were never installed); use `pack_items_clear`/`pack_item_delete`.
    Deletes and touches of missing rows are no-ops. Rows with a kind this build does not know are skipped (warn). `u64`
    sizes saturate at `i64::MAX`. Upserts write exactly the given values (including `installed_at`).
14. **Backups.** `backup_to` = `VACUUM INTO` a temp sibling → verify it read-only (`quick_check`, schema version) →
    delete stale `-wal`/`-shm` of the destination → atomic rename over it; the temp file never survives a failure.
    `user_backup_create(None)` writes `<data>/backups/user-YYYYMMDD-HHMMSSZ.qdb` (UTC; `-2`, `-3`… on a clash); a folder
    gets that name inside it; a file is replaced; blank or relative paths and a missing folder are `InvalidArgument`.
15. **Recovery.** `open_or_recover` quarantines on corruption (`SQLITE_CORRUPT`/`NOTADB`, failed `quick_check`) and on a
    failed migration, **including a database written by a newer build** (`DatabaseTooFarAhead`: the copy is kept intact,
    a later upgrade can open it). Transient failures (busy, locked, can't open, read-only, permission, disk full, I/O,
    out of memory, interrupted) are returned as errors and never quarantine a healthy file. `quick_check` runs only in
    `open_or_recover`. Note: SQLite itself deletes the `-wal`/`-shm` of a file that is not a database when the failed
    connection closes; when they exist, quarantine moves them with the file.
16. **Tombstone purge** also removes `item_tag` links of purged items (the table is polymorphic, without a foreign key);
    `collection_item` rows cascade. It returns the number of library rows removed.

## Requests

- **Lead (contract PR):** the §9.8 banner "Restore from backup…" has no command. Suggested addition to §5.13
  `commands/user_study.rs`: `pub async fn user_backup_restore(app, state, src_path: String) -> Result<(), AppError>`
  (WP2b's body: `UserDb::restore_from` + `UserDataChanged` with every kind + `SettingsChanged`). The core side is done
  and tested (`restore_from`: verified, in place, WAL kept, older schemas migrated, nothing changes on a bad file).
- **Lead (contract PR, optional):** a `search_history` `UserDataKind`; today search-history changes are reported as
  `history` (deviation 7).
- **Lead:** fix WP2b's two acceptance lines to the `-- <filters…>` form (deviation 1).
- **WP7c (settings store):** `resetToDefaults()` sets `defaultSettings()` optimistically, but the stored result keeps
  `uiLanguage`, `onboardingDone`, `hintsSeen`, `closeToTrayAsked` (deviation 5). Keep those four from the current value
  in the optimistic copy, or the UI flips to English (and could open onboarding) until the reply arrives.
- **WP9b (memo mock), WP10b (search mock), WP11c (user mock):** mirror deviations 9–14 in the browser mock (dedupe and
  caps, sparse `memo_progress`, set-status rules, validation errors, backup path shape).
- **WP4d:** the audio glue records `listen` history through `UserDb::history_record` directly, which emits no event;
  emit `UserDataChanged { kinds: [history] }` there if the History panel should refresh while listening.
- **WP2a:** shared helpers in `user_db/mod.rs`: `UserDb::now_ms()`, `ms_to_secs`, `opt_ms_to_secs`, `new_id` (UUIDv7),
  `col_u32`/`opt_col_u32` (stored integer → `u32`, `Corrupt` otherwise), `layout_from_db`, `check_ayah`,
  `check_ayah_range`, `check_page`, `DAY_MS`. `purge_tombstones(30)` at open already covers bookmarks, highlights, notes,
  collections and tags. `tests/support/user.rs` has `TempUserDb` (`new`, `at(ms)`, `reopen`) and `count(db, table)`.
